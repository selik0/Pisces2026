# Pisces2026 框架架构分析与下一步开发方向

## 一、总体判断

这是一个 Unity 客户端框架雏形，已经完成了比较完整的基础运行时骨架，核心目标是：

- 将业务逻辑从 Unity 场景脚本中剥离；
- 通过 `GameProject` 编译出多个 DLL；
- 由 `GameClient` 提供 Unity 环境适配；
- 使用 Manager 单例统一管理生命周期；
- 通过 FSM、事件、定时器、协程、场景、UI、资源、配置等模块支撑游戏业务。

当前框架的成熟度可以概括为：

> 基础设施已经成型，框架模块较齐全，但真正连接“客户端启动—更新—资源—网络—登录—主场景”的业务闭环尚未完成。

目前最明显的状态是：底层框架已经写了不少，业务流程仍然处于模板和占位阶段。

这个分层总体是合理的：

- `GameLogic` 放具体游戏流程；
- `GameClient` 负责 Unity 绑定。

这是一个适合中小型 Unity 项目的结构，也适合后续进一步拆分为客户端框架和具体项目逻辑。

## 三、核心框架分析

## 1. 启动和生命周期

Unity 入口位于：

```text
GameClient/Assets/Scripts/Runtime/GameLauncher.cs
```

当前流程：

```csharp
[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.BeforeSceneLoad)]
private static void Bootstrap()
{
    Platform.SetService(new PlatformImp());
    ManagerHub.Instance.Initialize();
}
```

然后由：

```text
GameEngine/Runtime/Base/ManagerHub.cs
```

统一初始化：

- 日志；
- Native 日志服务；
- Proto 配置日志服务；
- 协程；
- 定时器；
- 事件；
- FSM；
- Scene；
- UI；
- UI 跳转；
- UI Widget；
- Asset；
- 红点；
- Audio。

`ManagerHub` 还承担 Unity 主循环驱动职责：

```text
AssetManager.Tick
CoroutineManager.Tick
TimerManager.Tick
FsmManager.Tick
SceneManager.Tick
UIManager.Tick
UIWidgetManager.Tick
AudioManager.Tick
```

### 优点

1. 统一入口清晰；
2. 管理器初始化顺序固定；
3. 生命周期支持 `Login` / `Logout`；
4. 每个子系统异常由 `TickSafely` 隔离；
5. 登出时逆序清理；
6. 日志、原生服务、协议日志都有集中装配。

### 主要问题

#### 1.1 `ManagerHub` 同时承担太多职责

当前 `ManagerHub` 同时负责：

- 初始化；
- 运行时 Tick；
- Login；
- Logout；
- 日志装配；
- 各系统注册；
- 异常隔离；
- Unity MonoBehaviour 生命周期。

在项目早期比较方便，但后续会变成一个“巨型入口”。

建议未来逐步拆分为以下概念：

```text
GameBootstrap
    ├── RuntimeCompositionRoot
    ├── FrameLoop
    ├── SessionLifecycle
    └── ServiceRegistry
```

不一定要立即拆文件，但概念上应该逐步分离。

#### 1.2 Tick 顺序目前是隐式固定的

当前 Tick 顺序为：

```text
资源
协程
定时器
FSM
场景
UI
Widget
音频
```

这个顺序会影响业务行为，例如：

- 定时器回调中创建 FSM；
- FSM 状态中打开 UI；
- UI 回调中释放资源；
- 场景更新中切换场景；
- 回调中销毁当前系统。

建议后续引入更新阶段：

```csharp
public enum UpdatePhase
{
    Early,
    Logic,
    Scene,
    UI,
    Late
}
```

或者至少把 Tick 顺序写入框架文档，并为每个系统定义生命周期阶段。

## 2. 协程系统

文件位置：

```text
GameEngine/Runtime/Coroutine/
```

当前协程基于 `IEnumerator`，不依赖 Unity `MonoBehaviour`：

```csharp
CoroutineManager.Start(IEnumerator routine)
CoroutineManager.Stop(int id)
CoroutineManager.StopAll()
CoroutineManager.Tick()
```

支持等待秒数、等待帧、等待条件和自定义 YieldInstruction。

### 优点

- 脱离 Unity MonoBehaviour；
- 可以统一停止；
- 帧内新增协程不会影响当前遍历；
- 对生命周期清理有处理；
- 管理器接口比较简单。

### 后续需要验证

1. 协程内部异常是否完全隔离；
2. 嵌套 `IEnumerator` 是否支持；
3. 协程停止时内部资源是否释放；
4. `StopAll` 在回调重入时是否稳定；
5. Tick 过程中删除当前协程是否安全；
6. 是否需要协程句柄，而不是只返回整数 ID。

建议后续增加：

```text
CoroutineHandle
```

让业务持有句柄，而不是依赖裸 `int`。

## 3. 定时器系统

文件位置：

```text
GameEngine/Runtime/Timer/
```

当前支持：

- 一次性定时器；
- 重复定时器；
- 最大重复次数；
- scaled time；
- unscaled time；
- Tick 中延迟添加；
- Tick 中延迟停止全部。

设计比较成熟，尤其是 `_toAdd` 和 `_stopAllPending` 说明已经考虑了回调重入。

### 需要重点确认

- scaled / unscaled 时间是否使用了正确的 Unity 时间源；
- 时间缩放为 0 时行为是否符合预期；
- 长帧时重复定时器是否会瞬间触发大量逻辑；
- 定时器回调异常是否会影响后续定时器；
- 取消后是否立即回收。

建议明确重复定时器策略：

```text
策略 A：补齐触发次数
策略 B：每帧最多触发一次
策略 C：跳过过期周期，重新计算下一次
```

游戏业务通常建议默认采用“每帧最多触发一次”，避免卡顿恢复时瞬间触发大量逻辑。

## 4. 事件系统

文件位置：

```text
GameEngine/Runtime/Event/
```

当前 API：

```csharp
EventManager.Subscribe(...)
EventManager.Unsubscribe(...)
EventManager.Emit(...)
EventManager.Clear(...)
EventManager.ClearAll()
```

支持 0 到 3 个参数，并且支持在事件回调中订阅和取消订阅，延迟到最外层 Emit 完成后生效。

### 优点

- 使用泛型回调，避免 object 数组；
- 监听器变化延迟提交；
- 生命周期登录和登出时清空；
- 异常处理集中在 `EventBinding`；
- API 使用成本较低。

### 主要问题

#### 4.1 EventKey 是裸 int

裸 `int` 容易导致事件编号冲突、参数类型约束弱、业务代码可读性低。

建议至少统一事件常量：

```csharp
public static class GameEvents
{
    public const int LoginCompleted = 1001;
    public const int PlayerDataChanged = 1002;
}
```

更进一步可以支持强类型事件：

```csharp
EventManager.Subscribe<LoginCompletedEvent>(OnLoginCompleted);
EventManager.Emit(new LoginCompletedEvent(...));
```

#### 4.2 缺少生命周期绑定订阅

UI、场景、Brick、Widget 中如果手动管理订阅，容易遗漏解绑。

建议增加：

```text
EventBindingHandle
```

或：

```csharp
EventManager.Bind(owner, eventKey, callback);
```

在 owner 销毁或关闭时自动解绑。

## 5. FSM 系统

文件位置：

```text
GameEngine/Runtime/Fsm/
```

当前支持：

- 泛型 Owner；
- 多状态注册；
- 状态切换；
- FSM 管理；
- FSM 销毁；
- Tick 驱动；
- 生命周期清理。

`GameLoginFlow` 和 `GameUpdateFlow` 都使用了 FSM。

### 当前核心问题

FSM 基础设施基本具备，但业务 FSM 目前是“演示状态”：

```csharp
fsm.Owner.LoginSucceeded = true;
```

以及：

```csharp
fsm.Owner.ForceUpdateRequired = false;
fsm.Owner.HotUpdateRequired = false;
```

这意味着：

- 登录没有真实网络请求；
- 更新没有真实版本检查；
- 热更新没有真实资源下载；
- 登录数据没有真实同步；
- 流程无法处理异步回调；
- 失败、超时、重试、取消都没有实现。

### FSM 下一阶段应该支持

1. 异步状态；
2. 状态超时；
3. 取消；
4. 重试；
5. 错误转移；
6. 状态进入和退出原因；
7. 状态完成事件；
8. 状态调试信息。

建议状态流程统一成：

```text
Enter
    ↓
Request
    ↓
Waiting
    ├── Success → Next
    ├── Fail → Retry / Error
    ├── Timeout → Retry / Error
    └── Cancel → Exit
```

## 8. 资源系统

当前基于 Addressables，支持：

- 相同地址和类型合并加载；
- 引用计数；
- 缓存时间；
- 异步进度；
- 加载回调；
- 统一释放；
- 异常记录；
- Provider 抽象。

### 关键问题

#### 8.1 回调缺少可取消句柄

建议引入：

```text
AssetLoadHandle<T>
```

支持：

```csharp
handle.Cancel();
handle.Release();
handle.IsCompleted;
handle.Asset;
```

#### 8.2 加载失败和回调语义需要统一

当前失败通过 `onCompleted(null)` 表达，建议改为：

```csharp
AssetLoadResult<T>
{
    bool Success;
    T Asset;
    Exception Exception;
    string Address;
}
```

#### 8.3 Addressables 初始化和版本管理缺失

目前尚未看到：

- Addressables 初始化；
- Catalog 更新；
- 远端资源版本；
- 下载大小查询；
- 下载进度；
- 缓存清理；
- 资源包校验；
- 资源热更新。

这是下一阶段最关键的工作之一。

## 10. 本地存储和安全

`LocalDataStore` 已具备：

- JSON 序列化；
- 原子写入；
- 自定义相对路径；
- 路径越界保护；
- Release 模式 AES 加密；
- HMAC 完整性校验；
- 文件头；
- 版本号；
- 临时文件清理。

需要注意，客户端内置 AES 密钥只能提高普通用户直接查看和简单篡改的成本，不能作为服务端权威数据的安全基础。

适合存储：

- 本地设置；
- 新手引导状态；
- 非关键缓存；
- 客户端偏好；
- 本地进度的基础保护。

不应把关键资产、账号权限和货币数据的最终可信度建立在客户端存储上。

## 五、当前框架的主要短板

按照重要程度排序：

### P0：缺少真正可运行的主流程

目前实际业务流程仍然主要是：

```text
启动
    ↓
初始化 Manager
    ↓
Update
```

缺少完整链路：

```text
启动
    ↓
初始化平台
    ↓
初始化资源系统
    ↓
检查版本
    ↓
热更新
    ↓
平台登录
    ↓
连接服务器
    ↓
登录
    ↓
同步配置
    ↓
同步玩家数据
    ↓
进入主场景
    ↓
加载主 UI
```

### P0：网络模块尚未落地

## 九、最终评价

### 优点

- 分层清晰；
- 管理器体系基本完整；
- 生命周期意识较强；
- UI 设计已经具备一定生产化特征；
- 资源引用计数和缓存设计较好；
- 配置二进制格式有版本和 Schema 校验；
- 本地存储考虑了原子写入和完整性；
- 平台适配与 Unity 客户端分离方向正确。

### 当前主要问题

- 基础设施多，真实业务闭环少；
- 网络层还没有形成；
- 热更新还停留在占位；
- 登录流程是示例代码；
- 配置生成链路刚开始成型；
- 自动化测试缺失；
- 缺少框架级调试能力；
- `ManagerHub`、`AssetManager`、`UIManager` 后续需要控制复杂度。

下一阶段不建议继续盲目增加新的基础模块。最合理的方向是：

> 先用现有模块完成一个可运行的“更新—登录—主界面”垂直切片，再根据真实运行问题补网络、资源、UI、配置和测试能力。

这样能够最快验证框架设计，而不是继续积累大量暂时没有业务验证的底层代码。
